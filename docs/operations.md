# Installation, configuration, backup and recovery

This is a development milestone for a single Linux server and Debian/systemd agents. Run the fixture/container gates before installing it on infrastructure. No production deployment, live Debian helper operation or workstation administrative operation was performed during development. Windows and SSH are unimplemented.

## Build and run the server

Use Docker with Linux containers and Compose. The Dockerfile runs isolated fixture tests and vet/race gates before producing the server image. The embedded SQLite C engine requires CGO/GCC during the build; the supplied Debian build image provides them, and runtime images/agent hosts need compatible glibc. Do not build deployment binaries with `CGO_ENABLED=0`. No `.env` loader or embedded defaults create accounts. The example hostname is a placeholder; use the actual DNS name clients will verify.

1. Copy `deploy/server.example.json` to `deploy/server.json`, set `origin` to the exact HTTPS browser origin, and keep the two data/identity paths as shown. Do not add a trailing slash. The identity volume retains the CA private key and credential encryption key separately from SQLite.
2. Run `docker compose -f deploy/compose.yaml build`.
3. Run `docker compose -f deploy/compose.yaml run --rm phoenix init -config /etc/phoenix/server.json`. Initialization refuses an existing identity. The command reports the **path**, never the value, of the private `setup.token` file. Named volumes inherit image UID/GID 10001 ownership.
4. Through trusted local administrator access, copy the public `ca.pem` from the identity volume and install it as a trusted CA on browser and agent machines. Verify its fingerprint through an independent trusted channel. This trust installation must happen **before** sending the setup token, password or invitation. Do not use `curl -k`, HTTP, or a browser certificate-warning bypass. Alternatively install a real CA-issued server certificate/key using `tlsCert`/`tlsKey` mounts; its names must cover both listener hostnames. Phoenix still uses its separate internal CA for agent certificates.
5. Run `docker compose -f deploy/compose.yaml up -d`. Open the exact configured HTTPS origin, enter the bootstrap token and a 14–72 byte password, and enroll/verify TOTP (SHA1, six digits, 30 seconds). The token expires in 30 minutes; no account is active until MFA confirmation succeeds. Securely remove the used token file through trusted local access after setup.

The browser/enrollment listener is 8443 and the mTLS-only agent listener is 9443. Both require TLS 1.3; TLS 1.2 is not supported. The generated server certificate expires in one year and the CA in five years. Before server expiry, provision a new CA-trusted server certificate/key through the configured paths and restart Phoenix. Agent certificates last 24 hours and renew with a newly generated local key when fewer than six hours remain. Keep machine clocks synchronized. CA rotation is currently an explicit migration: preserve the old CA for existing agents while planning a controlled re-enrollment; automated CA rollover is release work.

Keep the mTLS listener end-to-end to Phoenix. An HTTP-terminating proxy cannot replace client certificate authentication. Browser proxy upstreams must also be HTTPS with server verification; do not introduce an unprotected HTTP backend. Configure TLS 1.3 on the browser edge as well. Phoenix validates exact browser Origin and does not trust forwarded identity or `X-Forwarded-For`; per-IP throttling therefore shares the proxy's address. Account for this in ingress rate limiting. No WebSocket origins are needed.

## Enroll a Debian agent

Use a trusted deployment channel to install the two Linux binaries. Build them in the Linux Docker build (`docker build --target agent-artifacts --output type=local,dest=./bin .`); never run the Linux helper on a development workstation. The exported directory contains `phoenix-agent` and `phoenix-helper`; do not put credentials there. Review the helper before enabling it.

On the **dedicated Debian acceptance/target host**, an administrator should:

- Create a system account/group `phoenix-agent` with no login shell. Install the agent root-owned at `/usr/local/bin/phoenix-agent` mode 0755 and helper root-owned at `/usr/local/libexec/phoenix-helper` mode 0755.
- Create root-owned `/etc/phoenix` mode 0755. Install `agent.example.json` as `agent.json`, readable by the agent but not writable by it (root:phoenix-agent, 0640). Install the trusted server CA as `trusted-server-ca.pem`. This certificate must arrive through a trusted channel; an invitation is not a trust anchor. An optional SHA-256 leaf pin supplements CA/hostname validation; it never disables either.
- Create `/var/lib/phoenix-agent` owned by the agent with mode 0700. This holds the locally generated private key/certificate bundle and durable job ledger. Do not clone this directory to another host.
- Install `helper.example.json` as `/etc/phoenix/helper.json` root:root mode 0600. Both this policy and the agent's policy must explicitly allow the exact service. Reboot is disabled by default in both. Do not use broad service patterns or add application services during development.
- Install `deploy/phoenix-agent.sudoers` as `/etc/sudoers.d/phoenix-agent` root:root mode 0440 and validate with `visudo -cf`. It permits only the helper, which validates action, exact unit and absolute deadline and rejects untrusted policy ownership/modes. The agent is never given a shell through sudo.
- For read-only logs of approved services, optionally add the account to `systemd-journal`. That group can read broader local journal content, so grant it only when required. Phoenix's server output permission and agent log allowlist still apply; don't mistake the group for per-unit OS isolation.
- Install the provided agent unit in `/etc/systemd/system/phoenix-agent.service`. It restricts filesystem access, home access, memory, tasks and address families. It deliberately cannot enable `NoNewPrivileges` while using the separate sudo helper boundary.

In Phoenix, create a single-use invitation (ten minutes) for a display name and groups. Transfer it in a private file readable by the agent, e.g. `/run/phoenix-enrollment`, without putting the value in a URL, shell argument, unit file or shell history. Run as the agent user:

```sh
phoenix-agent enroll -config /etc/phoenix/agent.json -invitation-file /run/phoenix-enrollment
```

Run `phoenix-agent identity -config /etc/phoenix/agent.json` on the target through your trusted channel. It prints only the public host ID, SHA-256 certificate fingerprint and expiry. Compare them with Host details, OS and addresses, then use **Verify enrolled identity** in Phoenix. Management dispatch is blocked until approval; the pending agent may send telemetry. Securely remove the invitation file, then start/enable the agent service. Enrollment never replaces an active identity. Create viewer/operator accounts and assign explicit host/group/action grants in Access & accounts; accounts start with no grants. All accounts require TOTP. Diagnostic access (`uname -a`), output access and administrative actions are independent grants.

## Lifecycle and jobs

Revocation requires recent password+MFA and exact host ID confirmation, closes tracked connections and blocks new jobs. Already executed operations cannot be undone. For deliberate re-enrollment, revoke first, stop the agent, archive its identity/ledger securely, then create an invitation naming that revoked host ID and confirm it. Keep the archive outside ordinary source and backup exposure. Generate a new key locally. The generation increments; unrelated new hosts get new IDs.

The agent atomically replaces a private identity bundle after renewal. If the server rotates the serial but the response or local atomic write is lost, the agent fails closed; revoke and deliberately re-enroll through trusted access. Seamless rotation recovery is remaining release work. Expired agents cannot authenticate renewal and also require re-enrollment. An advisory Linux file lock prevents two agents from sharing a state directory and releases automatically on a crash.

Restarts and reboot require a typed action, host confirmation and password/MFA within five minutes. The UI's Verify identity action refreshes that window; TOTP codes cannot be reused. A reboot result of `accepted` is not a completed reboot. A later measured, changed boot ID after dispatch sets `rebootObserved`; this proves a subsequent boot observation, not the physical cause of that boot. Never retry `uncertain` actions automatically. Investigate the target, reconcile receipts and issue a new job only deliberately.

One job executes per agent; queues hold at most 128 per host. Queue expiry is at most five minutes; execution at most 30 seconds, with the helper additionally capped at 25 seconds. The agent stores a job claim before acting and returns the stored receipt on duplicates. A crash after claim gives an uncertain result. Claimed IDs are retained (at most 10,000); newest 200 acknowledged outputs remain, older acknowledged outputs are removed while IDs remain. At capacity, archive and deliberately re-enroll rather than deleting tombstones on a running identity.

## Retention and recovery

Telemetry retains at most 240 samples/host and 24 hours, whichever comes first. Process/service snapshots cap at 100 entries; logs at 200 lines and shared command output at 64 KiB. Jobs/results retain 30 days after terminal state; audit retains 90 days. Sweeps run every 30 seconds. SQLite's page limit is 256 MiB with additional bounded WAL growth; five-host capacity is the acceptance target, not a claim that 500 busy hosts fit. Encrypted command output at rest is **not** implemented: protect the filesystem/volume and backups; only recoverable MFA/Canary credentials use the separate AES-GCM key. Plan disk monitoring and offline maintenance before capacity is reached. Agent ledgers are also bounded by the SQLite page limit. No unbounded scratch or production log collection is configured.

For a consistent initial backup, **stop Phoenix**, copy the complete data volume (database plus any WAL/SHM files), and separately retain the identity volume and configuration with restricted permissions and independent encryption. Do not copy only a live `.db` file. Do not put identity keys in the same unprotected backup set as SQLite. Record CA/server certificate fingerprints, configuration, source/image revision and agent generations in the recovery inventory. Keep backups outside the served web directory. Apply bounded backup retention (for example seven daily copies); this repository does not automate backup destinations.

Restore into an isolated, stopped instance using the same data and separate identity keys, same origin and correct UID/GID. Before exposing it, remove all restored browser sessions using local offline administrator recovery, because a restored backup can revive sessions or revocation state. Revoke/re-enroll agents whose state changed since that backup; until reconciliation, block the agent listener at ingress. Treat any restored dispatched jobs as uncertain; startup does this automatically and never requeues them. Restored queued jobs past expiry retire on the next sweep/exchange. Verify inventory, permissions, mapped source identity and audit history before reconnecting hosts. Test restoration on an isolated fixture, not your live databases.

If setup expired before completion, stop the server and run `phoenix setup-renew -config /etc/phoenix/server.json`; the new token is in a private `setup-renewed.token` file and old invitations to setup no longer work. If the administrator loses password/MFA, stop Phoenix and run `phoenix recover-admin -config /etc/phoenix/server.json -account <name>`. It requires local database and separate key access, writes fresh credentials to `admin-recovery.secret` (never stdout) and revokes all sessions. These offline commands refuse to overwrite an existing output file: archive/remove a previous recovery secret through trusted local administration first. Read the file through a trusted channel, enroll the new MFA, restart and securely remove it. A lost encryption key or CA private key cannot be reconstructed from SQLite; recover the separately retained key material or perform an explicit new installation and agent re-enrollment.
