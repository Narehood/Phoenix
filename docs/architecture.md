# Architecture

One Phoenix Go server owns a WAL-mode SQLite database and serves the built React dashboard over TLS 1.3. Separate retained identity files hold the agent CA and the encryption key; they must be backed up separately from SQLite. The server is the only writer. No queue broker or distributed database is required.

SQLite uses the maintained `mattn/go-sqlite3` driver with its embedded C engine. Server and agent binaries require CGO at build time and Debian-compatible libc at runtime; the Linux Docker build supplies GCC. This avoids the larger generated libc dependency graph of the initially considered pure-Go driver and keeps cold module downloads within the 256 MiB growth budget. Windows CGO-disabled compilation only checks source types against the driver's stub; it is not a working database build. No runtime Windows support is claimed.

An agent generates its own Ed25519 private key and CSR locally. An administrator issues a ten-minute single-use invitation for a new host ID or explicitly revoked identity. Enrollment uses authenticated HTTPS; possession of an invitation never replaces an active identity. The CA signs the CSR for that exact host and certificate generation. Before management, an administrator compares the public fingerprint/host ID through a trusted channel and approves that exact enrolled identity. The pending agent can send telemetry. The enrolled agent opens outbound mTLS requests to a dedicated listener. Agents expose no inbound management listener. Certificates expire and renew before expiry; every request checks the durable serial and revocation state.

Transport and platform interfaces separate delivery from host, permission, telemetry and job models. Initial transport is outbound HTTPS exchange. Future SSH must use keys, trusted host keys, refusal of changed keys and a restricted account; it has no implementation in this milestone. Initial platform implementation reads Linux procfs and invokes fixed systemd/journalctl argument vectors. A separate restricted helper handles allowlisted restarts and explicitly enabled reboot. Windows returns unsupported.

Jobs are durable before dispatch. Authorization is checked at creation and again at dispatch. Agent job IDs are durably claimed before execution. Delivery after a claim is never automatically retried as a new action. Lost delivery, agent crash or server restart after dispatch produces an uncertain outcome for reconciliation. Exactly-once execution across crashes is not promised. Reboot acceptance and observation of a new boot ID are distinct events.

Telemetry has measurement and server collection timestamps; a missing/stale agent is not proof of an uptime outage. Resource health requires fresh measurements. Canary monitor identity is the tuple of configured source and monitor ID, preserving each observing node and maintenance metadata. A missing Canary source changes source freshness to unknown/stale, not machine health.

Bounds: five-host acceptance fixture, 30-second collection, 240 retained samples per host, 100 processes/services per sample, 64 KiB command output, 200 log lines, one execution per agent, 128 queued jobs per host, 30-second job deadline and five-minute queue expiry. Audit/job retention and backup policy are explicit in operations documentation.
